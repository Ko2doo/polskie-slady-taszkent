# Translations

## The rule

Every piece of user-visible text goes through i18next, never hardcoded — including a
"temporary" button label, a placeholder, an `aria-label`, or a toast message added while a
feature is still in progress. If a feature touches the UI at all, its patch includes the
translation keys for all four locales, not a follow-up.

## The four locales

`src/locales/{ru,en,pl,uz}/` — `ru` is the default/primary language this project is
developed in; the other three must stay in step with it, not lag behind. Each locale has
(at least) `ui.js`, `errors.js`, and `articles.js`. Keep the same key structure across all
four files for a given namespace — a key present in `ru/ui.js` but missing in `pl/ui.js` is
a bug, not something to fix "later".

## Where a new key goes

- `ui.js` — anything shown directly in the interface: labels, button text, placeholders,
  hints, dialog titles, `aria-label`s. Nest by feature/component
  (`ui:map:mapEditor:photosAdd`, `ui:photoViewer:close`) rather than flat.
- `errors.js` — toast and error messages, including ones tied to a specific storage/feature
  problem (`customPointsStoreCorrupted`, `customPointsPhotoLimit`).
- `articles.js` — historical-place article title/description content, keyed by the place's
  id.

## Interpolation

Use i18next's `{{placeholder}}` syntax for dynamic values (`'Photos: {{count}} of {{max}}'`)
rather than concatenating strings. Keep the **same placeholder names** across all four
locales for a given key.

## Formatting long strings

Where a translated string would push a line over the project's line-length convention (see
`harness/code-style.md`), wrap it the way the existing locale files already do:

```js
photosHint:
  'Up to {{max}} photos. The first photo becomes the cover of the marker.',
```

## Checking parity

Before considering a change with new UI text done, verify every new key exists, with
matching interpolation placeholders, in all four locale files.
